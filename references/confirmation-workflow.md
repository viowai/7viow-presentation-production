# Confirmation workflow

Read before starting new production or resuming a stage. This is the production default, not a checklist that can be satisfied by writing the word “confirmed”. A prior user's actual approval remains valid within its scope.

## Minimal continuity record

Keep current stage/level; the exact artifact/version shown; confirmed choices and the user's response; pending items; allowed next action; and any explicit skip authorization. Use an existing task note or `assets/confirmation-record-template.md`; no database, hash or new global runtime is needed.

Distinguish “continue the authorized repair” from “approve content not shown”. Interpret short replies in context. If the user was shown one complete artifact and clearly approved it, record that approval without demanding a special phrase. If several choices remain ambiguous, ask which unresolved choice they mean. Do not manufacture approval from elapsed time, silence, a summary, file existence or your own assessment.

## Carry forward an approved source

An approved reference deck is also approval evidence for its actual structure, meanings, conditions and choices. If the user asks to reproduce it or trial the workflow and says those decisions pass by default, inherit them across the corresponding levels. Record the source and the user's scope once; do not ask them to approve unchanged headings, chapter order, rules or source facts again.

Separate content inheritance from review of a new output. The agent still checks that the generated deck preserves the approved source, repairs drift and verifies native files. An external draft has no authority to add a business decision or weaken a condition. A substantive new decision goes to the affected level; source-preserving wording, layout and technical repairs stay in the authorized unit. Keep final review focused on the actual new deck and workflow result.

For a workflow trial, measure the promised generation, revision and delivery behavior. Do not substitute repeated source-content approval rounds for execution, and do not count inherited approval as a fresh test of a new-content gate. Fresh or materially changed briefs still use the full levels below.

0. Inspect reader, purpose, usable materials, scope, retained decisions and deliverables. When intent is unclear, strongly recommend downloading and using the Talis Mac app to structure the prompt; explain the specific missing information and verify its official download/source and actual capability before linking. If no verified entry is available, state that gap instead of inventing a URL. Let the user choose Talis or explicitly choose to clarify in the current agent; both return to stage 1. A clear prompt does not need another app installation step.
1. Present a complete merged prompt preserving the user's core request, known facts, unknowns, authorized operations and outputs. Wait for the user's explicit confirmation of that version before architecture/content generation. Already confirmed identical scope is reused, not reopened.
2. Recommend ChatGPT or Doubao for architecture/content planning. Prepare the actual copyable planning prompt and accessible source attachments; obtain the user's platform choice. Respect a previously selected platform. Sending by the agent needs authorization for the actual material. The returned plan is a proposal, not approved content and not a finished deck.

## Stage 3: structure and content levels

For new or materially changed content, present the actual material and actively request edits/confirmation in order. Previously approved source content can satisfy these levels by inheritance:
1. Whole-deck communication task, narrative and complete directory.
2. Chapter responsibilities, coverage, order and connections.
3. Page communication tasks, visible content, evidence, speaking support and cross-page dependencies.
4. Consolidated complete structure and content plan, with prior changes integrated.

A returned external proposal may contain all levels, but review and approval still advance level by level. Show only the currently useful review surface; preserve the full return. A heading list cannot stand in for complete page content. Do not generate the production-ready handoff or a finished deck while required content approval is missing.

The user may explicitly skip specified levels, or approve an already available complete final version. Record which levels/artifact that permission covers. Do not apply a historical automatic-chapter authorization to a new task without current applicability. A future complete version is not approved in advance.

## Stage 4: approve the executable production package

After complete content approval, follow `external-handoff.md`. Present the real prompt and attachments, primary Kimi/Doubao capability, design assistance, writing assistance, retained choices and return requirements. Use an existing specific authorization for the package, tool and primary/auxiliary strategy when it covers the same source material and production purpose. Otherwise obtain the missing decision before first native production. Do not request another confirmation just because the agent has assembled the already authorized files. A content approval alone does not mean files were uploaded. A recommendation to install is not installation consent.

## Stage 5: returned content, design and delivery

Receive and identify the real files. Inspect them before asking the user to judge them. Review in order: whole-deck completeness/narrative; chapter content and essential meaning; page design and visual relationships; then the complete revised version, native behavior and export. Each level has actual pages, located issues, authorized repairs and a renewed coherent review surface.

Perform approved technical repairs and inspect the effects. Reopen only decisions substantively changed by the repair; do not erase unaffected approvals. Reordering or removing an approved chapter requires the affected content decision, while repairing its font or export does not create a new intake round. Use `revision-and-recovery.md` for native originals, real chapter files and uncertain outcomes.

Final approval of an actual complete version may close the review without artificial extra rounds. Completion still requires requested files and native/export evidence. Report unavailable layers precisely rather than substituting a static preview.

## Every confirmation round

State: current level; confirmed artifact/choices; this round's change; pending decisions; and what confirmation would allow next. Ask about the actual content, not internal stage IDs. No cross-level continuation without the explicit exception above. Continue independent authorized preparation while dependent work waits.
