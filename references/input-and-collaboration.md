# Inputs and collaboration

Read when preparing production or handing work to a contributor. Use existing context before asking. A table or machine schema is optional; the receiving person or tool must be able to act.

## Bind the input

Establish the reader and intended understanding or decision; delivery mode (spoken or standalone); requested output and editable format; current original; factual sources and their dates; accepted choices; requested changes; author and production method; asset availability; target application; output directory; and applicable permissions. Gather only what the actual task needs.

Assign source roles separately: current facts, business decisions, historic expression, style reference, asset, or quality benchmark. Confirm whether each is usable, pending review, historic, or withdrawn. Pending material can be reviewed when that is the request, but is not accepted authority. Withdrawn content is not rehabilitated through screenshots, extracts, a filename, or prior QA. If a source is withdrawn mid-task, remove its current dependencies and correct recommendations already sent within the authorized communication scope. Keep historical records as history.

Use the user's edited original for continuation. Check expected changes and representative content when multiple versions conflict. Do not turn a single style example into authority for facts, page structure, or public use.

Recover discoverable information directly. State a noncritical working assumption when it is useful. Ask only for a consequential unresolved choice or missing permission, with concrete impact. Missing assets may block a page without blocking unrelated preparation.

## Responsibility

The production coordinator owns the actual return, integration, verification coverage and delivery. A content owner integrates the narrative and necessary meaning. A native producer owns the actual layout, objects and export. A bounded contributor returns the requested help. These roles may be performed by one agent; naming roles does not create threads.

Supply each contributor with: the current objective and audience, named scope, readable inputs, retained decisions, allowed freedom, expected return, and authorized operations. A chapter additionally receives the adjacent argument it must connect to. Provide relevant text and source locations rather than the entire chat.

Require the return to identify the actual artifact, changes, preserved choices, missing inputs, checks performed and implications for the next unit. “Done” or a tool list is not an artifact. Inspect whether a claimed file actually exists and represents the requested revision.

## Existing writing skills

Deck can own supplied page content. Partner can contribute voice or concepts within the named task. Editor can repair specific prose while preserving page purpose. In autonomous mode, the user's selected creator can own narrative and copy; Deck then contributes only the requested context or content review.

Do not copy those skills into this package, force all three into every job, restart settled intake, or impose native-software QA on a content-only contributor. The stage-4 writing-skill recommendation and import verification remain required. Their installation is not mandatory: preserve a user-confirmed usable alternative. Missing required production capability must be reported precisely.
